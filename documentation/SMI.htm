System Management Interrupts (SMI)

Date: 12/16/2025

 

System management interrupts are high priority unmaskable hardware interruptions which cause the CPU to immediately suspend all other activities, including the operating system, and go into a special execution mode called system management mode (SMM).

Typically, the operating system has absolutely no control over when SMIs will happen or how long the CPU will subsequently stay in system management mode. In fact, the operating system is not even aware of the transitions to and from SMM, which makes troubleshooting the source and duration of the SMIs very difficult.

 

The concepts of SMI and SMM are specific to x86, but similar high privilege processor modes exist on other architectures. On ARM, for example, Secure Monitor Mode manages the switches between the Secure and Non-secure processor states.

The purpose of this article is to identify if SMIs are occurring, determine the impact of the SMIs, and identify methods to reduce the number of SMIs.

 

What is the impact of SMIs?

 

The firmware code (BIOS, UEFI) typically initiates the SMI. Once the SMI is generated, the state of the CPU is saved and the SMM code is executed on the SMM stack. Once the SMM code is complete, control is returned to the OS by restoring the state of the CPU. Thus, while a CPU is executing the SMM request, the OS is essentially "hijacked". The OS is unaware that an SMI has occurred and how much time the SMI took to execute.

 

SMIs are typically infrequent, but could last hundreds of microseconds, depending on what the interrupt needs to do. For most environments, SMIs can easily be ignored as they have a negligible impact on the overall performance.

 

However, the delays could impact sensitive low-latency applications, and the impact may vary depending on the frequency and duration of the SMIs. In a recent case, the SMIs were causing jitter on an audio streaming application. Identifying the cause and remediation steps were critical to the application’s success. Meanwhile, a high frequency market trading application is another example of a low latency application where microseconds make a difference between a successful trade and an unsuccessful trade!

 

Typical causes of SMIs

 

System Management Mode (SMM) is often used to control power management features and handling system events such as memory errors. An SMI is typically generated by firmware through features such as Integrated Lights-Out (iLO) by writing to the Advanced Power Management Control (APCM) register or other internal registers. Below is a list of some known causes of SMIs, but this list should not be considered as an exhaustive list.

 

·         iLO, including Redfish APIs accessing iLO features. This can include external system monitoring tools like HPE OneView, HPE Compute Operations Manager (COM), and other 3rd party monitoring tools using Redfish API. Note that not every Redfish API access to iLO will cause an SMI.

·         iLO Remote Console, especially when connecting and disconnecting from the Remote Console.

·         Advanced configuration and power management.

·         Detection and reporting of memory errors.

·         Operating system interacting with EFI.

·         During bootup as the OS identifies and configures hardware resources. Once the system is booted, the SMIs should be rare or infrequent.

 

Detecting SMIs and their frequency

 

For Intel x86 CPUs, the MSR_SMI_COUNT (0x34) model specific register contains the number of SMIs that have occurred in a system since boot. Each CPU core has access to its own MSR_SMI_COUNT register.

 

rdmsr

The rdmsr tool can be used to read the model specific register. Check with your Linux vendor for the appropriate package (such as msr-tools). Note that rdmsr needs root/superuser privilege.

 

The following rdmsr command will check CPU 0 to see how many SMIs have occurred since boot (value is in hexadecimal by default):

 

$ rdmsr -p 0 0x34

255c

 

0x255c SMIs sound like a lot, but most of the SMIs occurred during bootup. If you want to monitor all CPU cores for SMIs over time, you can use the following command which will update the SMI counters every 2 seconds:

 

$ watch -n 2 'rdmsr --all 0x34 | column'

One of the best ways to identify how often SMIs are occurring is by using the turbostat tool included in the kernel-tools package. Turbostat reads the MSR 0x34 register and determines the number of SMIs that have occurred since the last interval.

LinuxKI

The LinuxKI Toolset will report if an SMI has occurred, provided the SMI occurred during the traced period, which is 20 seconds by default. While LinuxKI tracing can be performed for longer than 20 seconds, it is not recommended unless the system is idle due to the amount of data that is logged. Due to the short duration of the trace, it is more difficult to capture an SMI unless the frequency and approximate time has already been determined.

 

To collect the SMI counts, you need to collect the data using the Advanced CPU Metrics option (-R):

 

$ runki -R

 

The kparse output and kirunq output will show the number of SMIs that have occurred during the trace. For example:

Identifying how much CPU is used by the SMIs

 

Detecting how much CPU is being used by the SMI can be difficult. The tools mentioned above can detect if SMIs are occurring, and the frequency can be approximated when monitoring over time. The tools discussed in this section detect latency, not specifically SMIs. But SMIs usually cause latency over 100 microseconds. When used with tools such as rdmsr and smi_watch.sh, especially in a server configured for low latency, the tools described in this section can be used to identify the amount of CPU used by each SMI.

 

These tools are often used on systems configured for low latency using the following whitepapers:

 

·         Low Latency Tuning for AMD EPYC CPU-Powered Servers (July 2024)

·         Configuring and tuning HPE ProLiant Server for low-latency applications (Edition 12)

Sysjitter is a popular opensource tool to measure CPU jitter delays. Note that the delays may or may not be caused by SMIs. It can be downloaded from the following URL:

 

https://github.com/Xilinx-CNS/cns-sysjitter 

 

Before running sysjitter, be sure to follow the appropriate Low Latency Whitepapers.

hwlatdetect

The hwlatdetect tool can be used to detect latencies and uses the built-in Linux hwlat tracer:

 

$ cat /sys/kernel/debug/tracing/available_tracers

hwlatdetect loops in kernel space, so it is not impacted by the scheduler or other running threads. Hwlatdetect can be impacted by SMIs, HT Sibling threads, and Turbo-boost frequency jitter. Case Study #1: Multiple SMIs seen at different intervals on DL380 Gen12 server

 

The customer reported CPU jitter delays in their low latency environment in hundreds of microseconds. Using the smi-watch.sh script, the SMIs were identified to occur during the following intervals.

 

·         Once every 10 minutes

·         Once every 5 minutes

·         Spurious SMIs at unpredictable intervals

 

After disconnecting the iLO Management lan, the SMIs which occurred every 5 minutes  disappeared. After updating to iLO 7 version v1.18 and updating the BIOS to v1.54, the SMIs on 5-minute intervals disappeared with the iLO Management lan connected.

 

Meanwhile, the customer found a Splunk forwarder calling df every 10 minutes. The df command with no options will display filesystem attributes such as free space for each filesystem on the server. Using strace to trace the df command, the following system call was observed:

 

statfs("/sys/firmware/efi/efivars", {f_type=EFIVARFS_MAGIC, f_bsize=1, f_blocks=507804, f_bfree=211500, f_bavail=206380, f_files=0, f_ffree=0, f_fsid={val=[0, 0]}, f_namelen=255, f_frsize=1, f_flags=ST_VALID|ST_NOSUID|ST_NODEV|ST_NOEXEC|ST_RELATIME}) = 0

 

Calling statfs() on the /sys/firmware/efi/efivars triggers the SMI as the efivars driver will make a call to firmware to get the attributes of the pseudo-filesystem.

 

To resolve the SMI every 10 minutes, the Splunk forwarder was modified to use df -x efivars to exclude the efivars filesystem type.

 

Finally, the customer found that OpsRamp was installed on the server as part of their standard build.   They removed OpsRamp and the spurious SMIs went away as well.   It’s possible that OpsRamp periodically calls df, but the actual trigger of the SMI is unknown.  

 

Operating system-generated SMIs are unusual, but as seen in this case study, can certainly occur. For more information on troubleshooting operating system-generated SMIs, see the Advanced Troubleshooting section at the end of this article.

 

Case Study #2: Poor audio stream quality on a ProLiant DL20 Gen11 server

 

Customer reported poor audio streaming quality on their DL20 Gen11 server.    Using sysjitter, HPE was able to determine there were some high jitter latencies, and smi_watch.sh was used to determine that SMIs were occurring periodically.    Further research and analyzing the AHS logs revealed that the customer had a script that runs every 30 seconds that queries the iLO via Redfish to execute the following:

 

/redfish/v1/systems/1 | jq .Oem.Hpe.AggregateHealthStatus <== slow causes SMI jitter

/redfish/v1/chassis/1/thermal

/redfish/v1/chassis/1/power

 

When the  script was stopped, the SMIs went away.    Additional investigation showed that getting the Power and Thermal attributes did not increase the SMI count.  However, when querying the System attributes to get the AggregateHealthStatus, a cache is the iLO needs to periodically be refreshed, which causes the SMI, and on a DL20, these SMIs can take several to hundreds of milliseconds.  

 

To reduce the frequency of the SMIs, the script was modified to collect the System attributes much less frequently, improving the audio quality significantly.

 

Troubleshooting SMIs

 

For the most part, there is no need to be concerned about the SMIs as they are a necessary part of the management of the system. However, in the case of latency-sensitive applications, where a customer needs near real-time behavior, the following troubleshooting is recommended:

 

·         The best suggestion is to follow the recommendations from the low-latency whitepapers.

·         Be sure to upgrade the latest BIOS/UEFI firmware version and the latest iLO firmware version as some SMIs get addressed in the firmware.

·         Disconnect the iLO Management lan to determine if the SMIs are triggered by something outside the iLO. If the SMIs go away, check for iLO redfish scripts, remote console access, or whether HPE Oneview or HP COM is configured to retrieve configuration, power, or similar data.

·         If SMIs are still observed after, collect the AHS logs for analysis by Support/ERT.

·         SMIs can be generated by the OS. While it is unusual, it can happen as seen in the Case Study #1 above. Identifying OS-generated SMIs can be done using LinuxKI and ftrace function tracing as described below.

 

Advanced troubleshooting for potential OS Generated SMIs

 

SMIs can be detected by the LinuxKI Toolset. LinuxKI will capture the SMI counter on every sched_switch event in the Advanced CPU metrics are enabled using the -R option with runki. For example:

 

$ runki -e all -R

 

The -e all option will collect some additional trace events such as workqueue_queue_work and workqueue_execute_start events.

 

Note that LinuxKI only runs for 20 seconds by default. If you are using LinuxKI on an idle system to capture an SMI, you can run it longer by using the -d option. For example, the following command collects trace data for 60 seconds:

 

$ runki -e all -R -d 60

 

Note that LinuxKI will add jitter, but the goal is to track down the SMI. To be certain that one or more SMIs can be detected during the trace, you need to be able to predict when an SMI will occur using tools like latency or smi_watch.sh. By observing the pattern, you can usually predict when an SMI will occur. Then the runki script can be 5-10 seconds before the SMI is expected.

 

The kirunq.<timestamp>.txt will show the number of SMIs that occurred for each CPU during the trace period. Note the SMI_cnt column on the right (the IRQ columns were omitted for clarity):

To dig deeper into the kernel functions executed on behalf of efi_call_rts(), the ftrace kernel function tracer can be used. Since df on the /sys/firmware/efi/efivars file system was determined to have caused the SMI, the following script was used to collect the ftrace kernel function trace of the df command:

 

# more functrace.sh

tag=`date +%m%d_%H%M`

HOSTNAME=`hostname -s`

savedir=$PWD

savebufsz=`cat /sys/kernel/debug/tracing/buffer_size_kb`

cd /sys/kernel/debug/tracing

echo 0 >tracing_on

echo 0 >trace

echo function >current_tracer

echo 16384 >buffer_size_kb

echo 1 >tracing_on

df /sys/firmware/efi/efivars

echo 0 >tracing_on

cat trace >$savedir/functrace.$HOSTNAME.$tag.txt

echo nop >current_tracer

echo $savebufsz >buffer_size_kb

cd $savedir

Examining the source code reveals the following code path was taken:

 

efi_call_rts()

  efi_call_virt()

   arch_efi_call_virt_setup()

      efi_enter_mm

        switch_mm

          switch_ldt

            load_mm_ldt

 

Exactly where the SMI is generated is not entirely clear. The source code for load_mm_ldt() does document that any change to the mm->context_ldt is followed by an IPI to all CPUs with the mm active. The switch_ldt() and underlying functions will trigger the switch to the SMM stack to execute the SMI code.
